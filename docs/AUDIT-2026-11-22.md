# CRABNNB security audit — 2026-11-22

## Executive summary

This review covers the current `main` tree at `482fe74` and the FR235 phone-bridge implementation. The PC-side Rust authentication and framing paths have substantial automated tests, and the Android relay has JVM tests for its protocol and orchestration. **The Garmin Connect IQ app, Garmin Connect Mobile, Android SDK callbacks, and physical FR235 have not been validated together.** A prior attempted Android SDK probe reported that no Garmin Connect IQ device was connected; no hardware tests were performed for this audit.

The implementation should therefore be treated as a **software prototype, not a verified hardware security control**. A valid bridge heartbeat proves possession of the shared key and freshness of a challenge response. In bridge mode it does not prove that the watch is physically nearby. The default configuration unlocks on verified presence but deliberately does not lock automatically.

## Scope and method

Reviewed the current Rust CLI, secure session, heartbeat verification, bridge TCP framing, monitor/action behavior, Android relay/SDK adapter/service, Connect IQ watch app, configuration/resources, and security documentation. Findings distinguish source-level observations from behavior requiring Garmin/Android hardware. The review did not read or expose any key material, run device probes, or claim a successful end-to-end hardware test.

## Current architecture and security properties

- **Direct BLE mode:** Linux raw HCI/L2CAP/ATT transport sends a fresh 16-byte challenge to the configured peripheral. Rust validates a ChaCha20-Poly1305 heartbeat, challenge echo, increasing counter, timestamp window, and configured RTT limit. A distance estimate from RSSI is additionally required before unlock. MAC and RSSI alone are not authentication.
- **FR235 bridge mode:** Rust connects to a phone companion over length-prefixed TCP on `127.0.0.1:8765` (typically through ADB forwarding). Android requires the Connect IQ SDK to initialize and exactly one connected device, sends the challenge to app ID `d72f71b21bf64c49a9ac3c6a670ea1f4`, and returns only an 81-byte watch response. Rust checks mode-1 AES-256-CBC + HMAC-SHA256, challenge echo, counter, timestamp, and RTT. Bridge mode has no RSSI/ranging; the configured MAC is not proof of physical presence in this transport.
- **Watch app:** API 1.4-compatible Monkey C code uses `Toybox.Communications`; its counter is read/written through `Application.getApp().getProperty("counter")` / `setProperty`. The timestamp is `Time.now().value()`. Android callback and Connect IQ behavior remain unverified on Garmin hardware.
- **Commands and locking:** unlock defaults to KDE Plasma `loginctl unlock-session`. The default locker is `loginctl lock-session`, but running it is opt-in through `--auto-lock` or a custom `--lock-cmd`. The monitor starts in a logical locked state and emits actions only on state transitions.

## Findings

| ID | Severity | Finding |
|---|---|---|
| F1 | **HIGH — release blocker** | The FR235 phone/watch/phone/PC path is not end-to-end validated. Source and JVM/unit tests cannot establish that the FR235 receives the challenge, executes the app callback, transmits a response, and reaches Android with the expected Connect IQ payload. A previous SDK probe reported no connected Connect IQ device. Do not rely on this bridge as an operational locker until a physical FR235 + Garmin Connect Mobile test passes. |
| F2 | **HIGH** | Shared-key provisioning through the Garmin Connect app setting may place the key in Garmin account/cloud synchronization; the watch app also supports a key embedded in a sideloaded resource, which is extractable from the app artifact. Anyone obtaining the PSK can impersonate the watch. Prefer a verified out-of-band provisioning process, do not commit or distribute keyed artifacts, and rotate the PC and watch key together after exposure. |
| F3 | **HIGH (proximity limitation)** | The phone bridge has no RSSI or ranging factor. Its HMAC authenticates a response to a fresh challenge but cannot establish the watch's physical distance. `--max-roundtrip-ms` is a software latency ceiling, not distance bounding; a sufficiently fast relay can pass. The direct-BLE RSSI signal is also relayable and is not a security-grade distance bound. |
| F4 | **MEDIUM** | The local TCP bridge has no peer authentication or transport encryption. Binding to `127.0.0.1` and using ADB forwarding avoids LAN exposure by default, but another local process (or a process with access to the forwarded endpoint) can submit challenges, consume watch responses/counter values, delay exchanges, or cause denial of service. It cannot forge a response accepted for the PC's independent fresh challenge without the PSK. Do not change the listener to a wildcard interface. |
| F5 | **MEDIUM — expected policy, operational caveat** | Automatic locking is disabled by default by design. Even with `--auto-lock`, the monitor initializes as logically locked; initial away/unverified samples do not emit a lock action until the monitor first observes a near/verified sample and later transitions away. Thus starting the daemon while the desktop is already unlocked and the watch is absent does not itself lock the desktop. This is not an unlock-authentication bypass, but users must not assume startup enforces a locked state. |
| F6 | **MEDIUM** | All deployments share one symmetric PSK. A compromised PC, phone, watch, Garmin account, or sideloaded binary can expose it; a compromised phone can generate valid watch-side responses. The protocol provides no per-device revocation or hardware-backed key isolation. Reprovisioning is required after compromise. |
| F7 | **LOW / documentation** | Earlier protocol documentation contained stale instructions and claims: `/etc/crabnnb/key.hex`, that the FR235 bridge app was not compiled, that counter storage used `Toybox.Storage`, and unconditional lock behavior after failed heartbeats. Current defaults use `~/.Garmin/crabnnb-pairing-key.hex`; the watch source uses app properties; and lock command execution is gated by auto-lock configuration. Corrections are included with this audit. |

## Mitigations verified in source

- Secure mode is the default; using legacy MAC+RSSI-only mode requires explicit `--allow-insecure`.
- Heartbeat validation checks message mode/size, authentication tag (constant-time comparison for HMAC), challenge echo, strictly increasing per-process counter, timestamp age/skew, and RTT policy. For bridge mode, HMAC is checked before CBC decryption.
- PC key files are rejected when group/other permission bits are set on Unix; key generation uses create-new semantics and mode `0600`.
- The Android listener binds to loopback. Relay failures, unexpected device counts, callback failures, malformed responses, and timeouts fail closed rather than fabricating a heartbeat.
- Automatic lock command execution is disabled by default; explicit `--auto-lock` or custom `--lock-cmd` opts in. This avoids unexpected lockouts but means unattended locking is not provided by default.
- Fresh random challenges prevent replay of previously captured responses as answers to a different challenge. Counters and timestamps are defense-in-depth, not substitutes for challenge freshness.

## Verification and limits

Current code and project documentation report Rust unit/integration coverage and Android JVM coverage, but automated tests do not exercise Garmin radios, Garmin Connect Mobile transport, Android lifecycle/SDK adapters, or a physical FR235. The Android JaCoCo configuration explicitly excludes Android lifecycle/service and Garmin SDK construction/callback adapters; they need device/instrumentation coverage. The watch code compiles against Connect IQ SDK 8.1.1 for `fr235` according to the current project build notes, but compile success is not runtime interoperability evidence.

For this audit, `cargo test --locked` passed (201 unit tests and 7 integration tests), `cargo build --locked` passed, `cargo fmt --all -- --check` passed, and `cargo clippy --locked --workspace --all-targets -- -D warnings` passed. `gradle -p phone-bridge-android check` could not run with the active Java 8 runtime; retrying with the installed Java 27 runtime got as far as Gradle configuration but failed because no Android SDK location is configured. No watch was connected and no hardware probe was run. Do not interpret unit tests, mock TCP tests, coverage reports, or compilation as end-to-end validation.

## Recommended next actions before operational use

1. Complete the documented FR235 + Garmin Connect Mobile + Android companion + PC challenge/response test and retain logs that exclude the PSK.
2. Verify that the pairing key is not synchronized or backed up by Garmin, and decide on a safe out-of-band provisioning workflow. Remove any embedded key from tracked resources/build artifacts.
3. Decide explicitly whether users want auto-lock. If so, consider a separate opt-in startup-lock policy and test it; do not silently change the safe default.
4. Keep the bridge bound to loopback and restrict local account access. Consider local authentication if the bridge is ever exposed beyond a single-user loopback/ADB setup.
5. Document the residual relay risk prominently; do not describe accepted RTT or valid HMAC as proof of proximity.
