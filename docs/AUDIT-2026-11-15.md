# CRABNNB security audit — 2026-11-15

Scope: full source audit of `crabnnb` v0.1.1 (3 commits on `main`) plus hardening
so that lock/unlock cannot be triggered by a spoofed MAC / fake RSSI (e.g. a
Flipper Zero). Target setup per user: **Garmin Forerunner 235 + Linux PC**.

## Architecture (as found)

`main.rs` -> `run::run_cli` -> raw HCI socket (`sys.rs` syscalls, no libbluetooth)
-> `HciTransport` -> `BleDevice`. Each poll: HCI inquiry + Remote Name Request
to the configured MAC (`device.rs::lookup_name`), then an L2CAP connect (PSM 1)
just to obtain an ACL handle for `HCI Read RSSI` / `Read TX Power`, converted to
a distance (`distance.rs`, log-distance path loss). `Monitor` (`monitor.rs`) is
edge-triggered: starts locked, unlocks on the first "near" sample, locks after
`--max-missed` far/away polls. Lock/unlock run user-configured shell commands
(`commands.rs`, `/bin/sh -c`).

## Findings

| # | Severity | Finding |
|---|----------|---------|
| F1 | **CRITICAL** | Presence decision = MAC match + RSSI only. Both are attacker-controlled: a Flipper Zero can claim the watch's BD_ADDR, answer the Remote Name Request, and transmit at high power so RSSI reads as "0 cm". One poll cycle then produces `Sample::Distance(small)` -> `Action::Unlock`. Nothing cryptographic is ever exchanged. |
| F2 | HIGH | No encryption or authentication anywhere on the watch<->PC path; no pairing/bonding is required; the L2CAP socket is only used to force an ACL link, never carries authenticated data. |
| F3 | HIGH (impact of F1) | The unlock path executes `--unlock-cmd` via `/bin/sh -c` as the user, so a spoofer doesn't just unlock the screen, they trigger whatever command is configured. |
| F4 | MEDIUM | HCI raw channel requires root/CAP_NET_ADMIN; the documented systemd unit runs as full root with no sandboxing. |
| F5 | MEDIUM | RSSI is a measurement of whoever transmits — meaningless against an active attacker; distance threshold alone is not a security boundary. |
| F6 | LOW | Exit code 3 documented as "command execution error" but also returned for "device not active"; `--scan-period 0` allowed (busy loop); "running lock/unlock command" printed even with `--quiet`; `io::Error::other` (Rust 1.74) used while MSRV is declared 1.70. |
| F7 | INFO | "Zero-dependency" means no system libs (libbluetooth); cargo deps already exist (lexopt, anyhow). |

## Hardening implemented

Unlock now requires **all** of: MAC match (still checked), a **fresh
ChaCha20-Poly1305-authenticated heartbeat** under a pre-shared 256-bit key, and
RSSI distance below threshold. A failed/missing heartbeat is treated as
"away" and locks after `--max-missed` polls.

- `src/crypto.rs` — AEAD wrapper (validated against the RFC 8439 vector), `/dev/urandom` nonces, hex key files with `0600` enforcement, `--gen-key-file` provisioning (create-new, never overwrites).
- `src/heartbeat.rs` — wire format: PC sends 16-byte random challenge; watch replies `nonce(12) || AEAD(counter u64le || unix-ms u64le || challenge echo, AAD = watch_mac || pc_mac) || tag`. Verification rejects bad tag, wrong challenge echo, non-increasing counter (replay), and timestamps outside `--heartbeat-window-ms`.
- `src/att.rs` + `src/transport.rs` — minimal GATT client over L2CAP ATT (CID 0x0004): MTU exchange (247; >= 63 required for the 60-byte heartbeat), Write Command to the challenge handle, Handle Value Notification from the heartbeat handle.
- `src/session.rs` — `SecureSession` probe state machine (outstanding challenge, last counter, freshness window).
- `src/hci.rs` — `Read BD ADDR` so the PC's own MAC goes into the AAD; `src/device.rs` — `secure_probe`/`local_mac`, ATT link in secure mode; `src/monitor.rs` — new `Sample::Unverified`; `src/cli.rs`/`src/run.rs` — new options, **secure-by-default** (no `--key-file` => refused unless explicit `--allow-insecure`, which prints a warning).
- New CLI: `--key-file`, `--gen-key-file`, `--allow-insecure`, `--heartbeat-window-ms`, `--challenge-timeout-ms`, `--challenge-handle`, `--heartbeat-handle`.
- Docs: `docs/secure-heartbeat.md` (protocol spec), README security section, hardened systemd unit (`AmbientCapabilities=CAP_NET_ADMIN`, `NoNewPrivileges`, `ProtectSystem=strict`), CHANGELOG.

## Why a Flipper Zero can no longer break it

Spoofing the MAC and blasting RSSI only gets the attacker past `lookup_name`.
The poll then demands a valid AEAD tag under the PSK, an echo of the challenge
the PC just generated (kills pre-computed/recorded answers), a strictly
increasing counter (kills replay), and a timestamp within the freshness window
(kills stale captures). The Flipper has none of these without the key file,
which never travels over the air and must be mode `0600` on disk.

## Forerunner 235 specifics (important)

Connect IQ **cannot host a GATT server**: `Toybox.BluetoothLowEnergy` is
central-role only and exists only on CIQ 3.1+ devices — the FR235 is not among
them. So the FR235 itself cannot run the responder this PC-side client expects.
Options (details in `docs/secure-heartbeat.md`): phone bridge via
`Toybox.Communications` + companion app, ANT+ channel to an ANT+ USB stick on
the Linux PC, a newer CIQ 3.1+ watch as BLE central against a BlueZ GATT server
on the PC, or any BLE peripheral (e.g. nRF52/ESP32 bridge) running the
reference responder. The `crypto`/`heartbeat`/`session` modules are
transport-agnostic and reusable for all of these.

## Residual risks + mitigations added after the audit

- Relay attacks: now bounded by a challenge round-trip-time limit
  (`--max-roundtrip-ms`, default 250 ms — a relay hop adds latency and is
  rejected), plus the RSSI distance factor in direct-BLE mode, plus documented
  hardware distance bounding (BLE Channel Sounding / UWB) for capable radios.
  See `docs/phone-bridge.md#relay-attack-mitigation`.
- Phone-bridge path for the FR235 (which cannot host GATT): `iq-phone-bridge/`
  Connect IQ app + `phone-bridge-android/` companion + `crabnnb --bridge-addr`,
  using an AES-256-CBC + HMAC-SHA256 heartbeat (mode 1) that Monkey C can
  compute; verified on the PC side with RFC 4231 / NIST vectors and
  forgery/replay/stale/RTT tests (140 unit + 7 integration tests pass).
- Key compromise = game over; rotate with `--gen-key-file` and re-provision.
- BLE link encryption (LE Secure Connections pairing) recommended as
  defense-in-depth; the heartbeat carries no secrets, so the AEAD/HMAC tag
  alone defeats spoofing even on an unencrypted link.

## Verification

- `cargo test`: **124 unit + 7 integration tests pass** (incl. RFC 8439 AEAD
  vector, forgery/tamper/replay/stale/wrong-challenge rejections, and run-loop
  tests proving garbage, missing or replayed heartbeats never unlock).
- `cargo build --release`: clean.
- Smoke: `--help` lists the secure options; running without `--key-file` exits 1
  with guidance; `--gen-key-file` produces a 64-hex-char file with mode `0600`
  and refuses to overwrite.
